[1]
For version one, the best fit is a small internal AWS web application built as a static React frontend on S3 + CloudFront, a Python FastAPI backend on AWS Lambda behind API Gateway HTTP API, Amazon Cognito for sign-in, Amazon S3 for uploaded result artifacts, and your existing RDS instance if it has headroom, with a new dedicated schema or database for this app rather than mixing tables into the current live trading schema. This keeps the UI modular, keeps hosting costs low for ~5 users, aligns with your current AWS estate, and avoids redesigning the training jobs now. HTTP APIs support JWT/OIDC auth and built-in CORS, API Gateway has no minimum fees, Lambda is pay-per-use, Cognito managed login is the lowest-effort hosted sign-in path, and S3 presigned uploads let the browser send files directly to S3 without passing file binaries through your API. [2]
On database choice, the most economical and fastest path overall is usually reusing your existing RDS instance if you can isolate this app with a separate schema/database, DB user, and security group rules. A new dedicated RDS instance adds a predictable ongoing baseline because RDS bills DB instance hours while the instance is running, plus storage and backups. DynamoDB can be cheaper in pure infrastructure terms for tiny, low-volume workloads because it avoids an always-on database instance and charges primarily for requests and storage, but your domain model is naturally relational: algorithms, versions, training models, results, and artifacts. For this use case, the engineering simplicity of RDS outweighs the likely DB bill advantage of DynamoDB. Cognito is also effectively negligible for 5 users because the user-pool free tier covers up to 10,000 monthly active users on the Lite or Essentials tiers. [3]
The recommended delivery model is phased. Phase one is a registry-and-results portal: CRUD for Algorithms, Algorithm Versions, Training Models, and Training Results, plus offline execution in your existing app and upload of CSV/JSON artifacts for visualization. Later phases can add live training orchestration using Step Functions and AWS Batch, which AWS documents specifically as a fit for orchestrating batch workloads and machine-learning-style pipelines. [4]

Recommended AWS architecture and cost position
The architecture below is the best balance of simplicity, modularity, AWS alignment, and low operating cost for your first version. CloudFront can securely serve content from a private S3 origin using Origin Access Control, HTTP APIs support OIDC/OAuth and CORS, Cognito managed login gives you a ready-to-use hosted sign-in flow, and Lambda can connect to RDS directly in simple scenarios or via RDS Proxy later if traffic patterns justify it. Why I recommend RDS over DynamoDB here
Your v1 use case is not an event stream or a key-value store. It is a small internal administrative system with versioned relational entities and obvious joins:
one Algorithm has many Algorithm Versions;
one Training Model can be used across many Training Results;
one Training Result belongs to one Algorithm Version and optionally one Training Model;
one Training Result has many uploaded artifacts.
That maps directly to a relational schema. DynamoDB’s raw billing model can be very attractive for low-volume systems because you avoid an always-on database instance and mostly pay for request units and storage, but the data model itself would become more complex for very little user-visible benefit. By contrast, RDS pricing is driven by DB instance hours, storage, backup storage, and optional IOPS. So the decision rule is straightforward: if you can piggyback on an existing RDS instance safely, do that; if you must create a brand-new datastore, DynamoDB may look cheaper on monthly infrastructure alone, but it is still the wrong abstraction for this v1. [7]

Future-state extension without redesign
For live model training later, the cleanest path is to keep today’s web app as the control plane and add a workflow plane:
the website submits a training request;
Step Functions coordinates the workflow;
AWS Batch runs a containerized training/backtest job based on your existing Python code;
results land in S3 and status rolls back into RDS.
That is a natural future state because AWS positions Step Functions as a workflow orchestrator for distributed applications and ML-style pipelines, and it supports calling AWS Batch directly for batch workloads. For recurring training schedules, AWS now recommends EventBridge Scheduler instead of legacy scheduled rules. [9]
Database schema and API design
The screenshot’s four-entity idea is directionally correct, but I would make one important enhancement: separate result metadata from uploaded artifacts. Do not put CSV or JSON blobs into RDS unless they are tiny and specifically needed for fast UI display. Keep relational metadata in RDS, keep files in S3, and store only the result summary and optional precomputed chart preview in the database.

Authentication approach
For five internal users, the best fit is Cognito User Pools with managed login on the frontend and API Gateway HTTP API JWT authorizers on the API. AWS calls managed login the lowest-effort integration path for web apps because Cognito hosts the sign-in flow for you, and HTTP APIs natively support JWT/OAuth/OIDC authorization. That gives you a secure system with very little custom auth code. I would define three groups from day one: admin, editor, and viewer. [12]

Frontend and repository workflow
For the frontend, I recommend React + TypeScript + Vite + React Router + TanStack Query + Tailwind CSS. React gives you a component model that is well suited to internal tools, Vite builds optimized static assets suitable for static hosting, React Router gives you straightforward client-side routing for a dashboard-style SPA, TanStack Query handles the messy parts of server-state fetching and caching, and Tailwind generates static CSS from the classes used in your templates with no runtime styling engine. In a small internal app, that stack is modern, clean, very modifiable, and easy for Codex to work with. [14]

CI/CD and deployment workflow
The infrastructure layer should be AWS CDK in Python. AWS positions CDK as a CloudFormation-backed IaC tool with repeatable deployments and rollback on error, and your current uploaded application is already CDK-based. For deployment from GitHub, use GitHub Actions with AWS OIDC federation so you do not need long-lived AWS secrets in GitHub. Protect the main branch and require pull-request review before production deploys. [16]
